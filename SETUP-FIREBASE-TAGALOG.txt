JAT GOLDEN GRAINS TRADING — FIREBASE SETUP

IMPORTANT
- Ang program na ito ay gumagamit na ng Firebase Authentication (Email/Password) at Cloud Firestore.
- Admin email: aries.calinga@gmail.com
Cashier email na awtorisado sa program: jatgoldengrainstrading@gmail.com
- Huwag ibigay kaninuman ang iyong Firebase password.
- Huwag i-publish ang Firestore Rules na nagbibigay ng read/write access sa lahat.

STEP 1 — FIRESTORE RULES
1. Buksan ang https://console.firebase.google.com/
2. Piliin ang project: jatgoldengrains
3. Pumunta sa Build > Firestore Database > Rules.
4. Palitan ang rules ng nasa ibaba at pindutin ang Publish.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /businessData/main {
      allow read, write: if request.auth != null
        && request.auth.token.email in [
          "aries.calinga@gmail.com",
          "jatgoldengrainstrading@gmail.com"
        ];
    }
  }
}

Ang rules na ito ay nagbibigay ng access sa Admin at sa nakatalagang Cashier email lamang. I-publish lamang ito kapag nagawa mo na ang Cashier account sa Firebase Authentication.

MAHALAGANG LIMITASYON SA KASALUKUYANG DATABASE STRUCTURE:
Nasa iisang document (businessData/main) ang lahat ng products, customers, sales, orders, expenses, purchases, payments at panukli. Dahil dito, ang pagpayag ng Firestore read/write sa Cashier ay nagbibigay sa account na iyon ng kakayahang basahin at baguhin ang buong document sa antas ng database, kahit nakatago ang Admin buttons sa interface. Nililimitahan ng app ang nakikitang UI, ngunit hindi ito kapalit ng tunay na database-level permissions. Para sa mahigpit na proteksiyon (hal. bawal baguhin ang completed sales o expenses), kailangang ilipat ang records sa magkakahiwalay na collections at magtakda ng per-collection rules o gumamit ng trusted backend. Huwag gamitin ang Cashier account kung hindi mo pinagkakatiwalaan ang taong may hawak nito.

STEP 2 — CHECK AUTHENTICATION
1. Sa Firebase Console, pumunta sa Build > Authentication > Users.
2. Tiyaking naka-enable ang Email/Password sign-in method.
3. Sa tab na Users, piliin ang Add user at gumawa ng account gamit ang email jatgoldengrainstrading@gmail.com at isang malakas na pansamantalang password. Ibigay ang password nang pribado sa Cashier; huwag ilagay sa code o GitHub.
4. Huwag gumawa ng Cashier account bilang Admin. Ang app ay awtomatikong magtatalaga ng CASHIER role sa eksaktong email na ito at tatanggihan ang ibang email.
5. Gamitin sa pag-login ang email at password na itinakda sa Firebase Authentication, hindi ang dating local username/password ng lumang program.

STEP 3 — I-UPDATE ANG GITHUB FILES
1. I-extract ang ZIP na ito.
2. I-upload/palitan sa iyong GitHub repository ang index.html, css/style.css, js/app.js, at assets/logo-jat.jpg. Maaari ring i-upload ang SETUP-FIREBASE-TAGALOG.txt.
3. Panatilihin ang folder structure: index.html, css/style.css, js/app.js, assets/logo-jat.jpg.
4. Hintaying matapos ang GitHub Pages deployment.
5. Buksan ang site at mag-login gamit ang Firebase email/password.

STEP 4 — UNANG PAG-LOGIN / DATA MIGRATION
- Kapag may existing jgg_state data sa browser kung saan unang mag-login at wala pang businessData/main document sa Firestore, kukunin ng program ang data na iyon at ililipat ito sa Firestore.
- Kapag may laman na ang businessData/main, ang Firestore ang gagamitin bilang pangunahing data source.
- Huwag burahin ang lumang browser data o ang Firestore document habang hindi pa nakukumpirma ang migration.
- Sa unang setup, mag-login muna mula sa device/browser na may pinakabagong existing data. Ang data na nasa ibang device/browser na localStorage lamang ay hindi awtomatikong pagsasamahin; kailangang i-migrate nang hiwalay bago ito mawala.

PAALALA SA DATABASE
Sa unang bersyon na ito, ang business records ay nasa isang Firestore document: businessData/main. Ang bawat save ay nag-a-update sa shared record, at ang ibang device ay tumatanggap ng live updates. May Firestore document size limit, kaya kung lumaki nang husto ang sales/history data, dapat ilipat ang records sa magkakahiwalay na collections.

TROUBLESHOOTING
- auth/invalid-credential: mali ang email/password o hindi iyon ang Firebase user.
- Firestore permission-denied: tiyaking na-publish ang Rules sa itaas at eksaktong tama ang Admin/Cashier email.
- Cashier login: tiyaking ang jatgoldengrainstrading@gmail.com ay nasa Firebase Authentication > Users at tama ang password.
- Blank/old app after GitHub update: hard refresh (Ctrl+F5) o buksan sa private/incognito window.

STEP 5 — ADMIN-ONLY BACKUP DATA
- Pagkatapos mag-login bilang Admin, pumunta sa Dashboard at pindutin ang Backup Data.
- Ida-download ng browser ang JSON backup ng kasalukuyang Firestore document businessData/main.
- Ang backup ay read-only: hindi nito binabago o binubura ang Firestore data.
- Itago ang backup sa ligtas na lokasyon. Huwag itong i-publish sa public GitHub repository dahil naglalaman ito ng business records at customer information.
- May Admin-only na Restore Data button. Pumili lamang ng backup JSON na ginawa ng Backup Data button at para sa project jatgoldengrains.
- Bago mag-restore, susuriin ng program ang format at laki ng backup, at hihingi ng kumpirmasyon. Susubukan din nitong i-download ang kasalukuyang Firestore data bilang Pre-Restore Backup bago palitan ang records. Kung hindi na-download ang safety backup, piliin ang Cancel.
- Ang restore ay papalit sa kasalukuyang laman ng businessData/main; ang mga pagbabago matapos ang petsa ng backup ay maaaring mawala. Huwag gamitin para pagsamahin ang magkakaibang backup.
- Huwag i-edit ang JSON file. Itago ang backup sa ligtas na lugar at huwag itong i-publish sa public GitHub repository.
